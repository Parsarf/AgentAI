## Work and completion criteria

Validate the complete product with a small controlled beta, including real customer accounts and payment lifecycle, before open paid signup.

1. Prepare onboarding/support materials, a named beta cohort/capacity limit, task allocations, feedback capture and success/incident metrics from Phase 1. Invite or message people only when explicitly authorized; otherwise deliver invitation drafts and a concrete readiness package. Select test versus live billing honestly. Real live payment proof needs an authorized consenting participant/provider account.
2. Run the example from a linked customer's real Telegram channel: sourced research → scope/plan → native Codex build → tests → restricted browser verification → fresh independent ACP review → fixes → versioned ZIP handoff. Let the runtime perform the work; operator inspection must not secretly replace a failed agent build. Retain correlated IDs, sources, commands, tested/reviewed hash, cost/receipts and decisions.
3. Follow the same task in the dashboard, leave/reconnect/refresh, select a project in Telegram, observe progress and final artifacts, download/reproduce the app, and continue the same conversation. Demonstrate budget stop/partial output and a failed-task/retry path with disposable work. Verify account B can use its dashboard/history/artifacts and queue/cancel work while A runs, then execute its own task after A drains, and cannot access A through guessed IDs/URLs. Use at most two invited accounts and one global running task on the existing VPS; do not require an upgrade. Parallel task capacity remains a separate later gate.
4. Observe actual beta billing: account/customer mapping, hosted checkout, entitlement activation from verified webhook, invoice, cancellation and payment-failure recovery. Provider test events prove the adapter; launch's required real beta accounts/payments still need actual live evidence. Never perform unauthorized charges or pretend test mode is live.
5. Gather consented real-task feedback/support incidents; classify failure patterns, fix defects, rerun affected acceptance and measure onboarding/task success/cost/support burden. Freeze meaningful sample/observation criteria before judging readiness; no invented testimonials or uptime claims. Maintain known limits and disconnected required-service blockers.
6. Provide a concise handoff: customer capabilities/limits, project start/test/download steps, integration/link/revoke/memory/schedule controls, retention/usage, support contact and operator restart/update/rotate/restore/rollback runbook. Document the actual owner and customer boundaries distinctly.

Deliver beta results, complete correlated workflow, reproducible bundle, payment evidence, fixed findings and customer/operator guides. Done when real authorized beta accounts complete the product workflow within enforced budgets and the agreed beta exit criteria pass, including required payments. Missing participants/auth/budget is a concrete blocker, not a completed beta.
