# Registry documents and artifact interactions

Lumina has one generated renderer contract: `lumina/src/gen/schemas.ts`, `catalog.ts`, `constraints.ts` and `registry.ts`. Its server JSON, examples and capability index are generated by `GEN_WRITE=1 npx vitest run src/gen/export.test.ts` from the Lumina directory. The server and renderer both validate untrusted documents. No generated JavaScript, HTML, SQL, shell or expression is executed.

## Discover and validate

Cells receive `lumina-ui/index.json`, one `lumina-ui/components/<id>.json` per registered capability, and `lumina-ui/validate.py`. The compact capability index is injected only for medium/interactive answers. Retrieve individual schemas and examples with the runtime's file tools, then run `python3 lumina-ui/validate.py draft.json` to get corrective errors before emitting the document. Do not read the full schema bundle every turn.

Authenticated clients can use `GET /v1/genui/registry`, `?component=<id>`, and `?root=1` for recursive schemas. Each entry carries its stable id/name/category, purpose, selection guidance, requirements, examples, schema reference, supported actions, composition/accessibility rules and runtime states. A registered presentation component does not imply that an external provider or credential is configured.

## Create

The assistant writes prose followed by one `lumina-doc` fence. Its body is a JSON document, or JSON Lines containing a header, complete datasets and complete blocks. Incomplete JSON is never mounted. Creation is anchored to the authenticated conversation and source request on the server; the model cannot select another account or conversation.

```json
{"version":"1.0","responseId":"comparison","blocks":[{"id":"options","type":"table","props":{"columns":[{"id":"name","label":"Option"},{"id":"price","label":"Price","type":"number"}],"rows":[{"name":"A","price":10},{"name":"B","price":12}],"searchable":true}}]}
```

Illustrative values above are protocol examples, not live results. Production documents must use verified task data. Limits: 24 top-level blocks, 60 total nodes, depth 3, 48 KiB documents, 60 inline rows or 500 dataset rows, bounded field strings and arrays. Node ids are stable within an artifact and unique throughout its composition. Child rules come from container schemas. Expensive media, charts, diagrams, math and model viewers load lazily.

## Update the same artifact

A submitted interaction resumes the same conversation's native agent session through a new admitted request. The server supplies the artifact id/version, node/action identity and current document in request context. The assistant emits a JSON document with `artifactId` and `baseVersion` plus its updated blocks. Only the artifact bound to that continuation in that conversation may be updated. Stale versions never overwrite newer work.

Authenticated clients can also call `POST /v1/genui/artifacts/{id}/update {version, document}`. This strictly rejects unknown properties/components/actions, duplicate ids, dangling graph edges, invalid dates and excessive composition. Compatible local state survives by node id, type and field definitions. Changed field definitions reset their old answers. Historical stored `type: document` envelopes are normalized at the renderer boundary.

## User state and events

`GET /v1/conversations/{id}/blocks` returns `state`, document `version`, and independent `state_revision` for documents. `POST /v1/genui/artifacts/{id}/state {version,state_revision,state}` saves bounded local state with compare-and-swap; conflicts return 409. A visible error reports failed autosaves. Tabs, filters, inputs, editable cells, checklist items and other local values use stable node ids.

Agent actions use `POST /v1/genui/artifacts/{id}/events`:

```json
{"id":"unique-event-id","node_id":"choices","action_id":"submit","version":1,"values":{"quantity":4}}
```

The server resolves the action from the stored node, validates submitted fields/options/bounds, and persists actor, account, conversation, artifact, node, action, version, payload and result. Identical event ids replay the original result; changed payloads under an old id are conflicts. Concurrent pending events are refused; expired claims can retry using a deterministic queue key. Failed attempts remain recorded and may be corrected/retried. Buttons/forms show pending, success and failure states. Local sort/filter/expand/select/update and internal navigation do not resume the agent.

Approval, denial and retry events use the actual native plan/request mechanism, scoped to this conversation. An approval artifact grants no permission by rendering. The phase must still be awaiting approval (or failed for retry); ownership, cancellation and current state are rechecked by the native runner. Native plan editing and launch continue to use their existing backend controls.

## Files and historical data

`file:<relative path>` resolves only if referenced by this stored document and owned by its conversation project. `GET /v1/genui/artifacts/{id}/asset?path=...` rechecks authorization, scanned-upload state or generated-artifact tickets, safe MIME types and preview size. `&download=1` returns an attachment. Documents cannot auto-load arbitrary third-party images or files. PDF/document iframes are sandboxed; GLB external resources are blocked; Mermaid diagrams are strict and isolated behind a CSP with no scripts, network or same-origin access.

The retired `lumina` protocol is no longer taught, produced or extracted. Historical tables, charts and comparisons migrate through a read-only adapter into the current registry renderer. Unrecognized historical results remain readable text/code with the original conversation data preserved. Historical account-owned picture blobs remain readable; the old remote page/image-fetching system and its switches were removed.
